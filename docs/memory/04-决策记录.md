# 04 · 决策记录（ADR）

> 只记"为什么这么定"，不记执行过程。执行过程在 03-轮次日志。
> 状态：`已采纳` / `已废弃` / `待评估`

## ADR-001 · 项目记忆落盘，不依赖模型上下文
- 日期：2026-11-22
- 背景：单个会话上下文有限，长项目必然遗忘；换 Agent 后历史断层
- 决策：所有目标、任务、进度、决策、协作规范写入 `docs/memory/`；任何 Agent 读文件接手
- 取舍：多花维护文件的力气，换来不丢记忆、可回滚、可换人
- 状态：已采纳

## ADR-002 · 分轮 + 闸门 + 独立对抗审查（拒绝"一次性多子智能体"）
- 日期：2026-11-22
- 背景：一次性塞大计划让 AI 自动委派一堆子智能体，结果质量差、无法验收
- 决策：一次只开一个任务；执行与审查分离；审查独立会话 + 换模型；只看证据
- 取舍：慢一点（每轮多一次审查），换来可控、可追责、质量稳定
- 状态：已采纳

## ADR-003 · 模型分工：豆包当主力，别家只做关键节点第二意见
- 日期：2026-11-22
- 背景：豆包额度充裕，qoder/codebuddy 额度少
- 决策：执行用 `Doubao 2.1 Pro`（或 `Qwen 4 Max`）；日常审查用 `DeepSeek V4 Pro`（同额度、异模型）；大版本发布前可用别家 CLI 做一次跨厂商抽查
- 状态：已采纳

## ADR-004 · 审查必须产出 PASS/FAIL + 证据，不接受"我觉得没问题"
- 日期：2026-11-22
- 决策：审查输出固定格式第一行 PASS/FAIL，其后附实际读取/执行结果
- 状态：已采纳

## ADR-005 · 反假成功宪章（最高施工纪律，源自 13 轮坑全集）
- 日期：2026-11-22（交接包第 9 节灌入）
- 决策：要么真实现，要么 not_implemented/unsupported + UI 置灰"规划中"；失败必须报原因；只看代码写完就报完成=不合格；每项以真实运行效果验证
- 背景：曾发生企业 8 模块假 ok、键盘未装仍 ok、Sprint 零任务谎报完成、OCR 猜字等
- 状态：已采纳

## ADR-006 · 全量采集模式（单人自用）
- 日期：2026-11-22（用户早已拍板，交接包确认）
- 决策：exclude_apps 默认空；privacy 三开关默认关；全量截屏送 AI 分析；redactor 保留可配置；README 口径与实现一致
- 状态：已采纳

## ADR-007 · 企业域 A 路线（诚实裁剪）
- 日期：2026-11-22（交接包确认）
- 决策：300+ 仿真端点不做实，插件包默认不注册；宣称撤回或标注"演示"；承诺的都能兑现，兑现不了的就撤回
- 状态：已采纳

## ADR-008 · 运行纪律（事故沉淀）
- 日期：2026-11-22（交接包第 9/10 节灌入）
- 决策：只用 Python311 完整路径解释器；Electron 独占后端生命周期，禁止并行独立起 main.py；重启前杀旧 python/node/electron；动数据先备份
- 背景：双后端 SO_REUSEADDR 双绑 59300 token 打架 401 事故
- 状态：已采纳

## ADR-009 · UI 视觉基线制度
- 日期：2026-11-22（轮 12 制度，交接包确认）
- 决策：`evidence-round12/visual-baseline/` 五图为唯一视觉基准；任何 UI 改动必对比基线 + 坐标断言验收；UI 需求先对齐目标态再动手
- 状态：已采纳

## ADR-010 · 账目与汇报纪律
- 日期：2026-11-22（交接包第 9/10 节灌入）
- 决策：数字只报提交态，与事实一致；矛盾用实测对平禁止辩解；每项自带实证再报完成；汇报 ≤10 行、第一行报账本、决策项单拎；反馈走对话框禁生 .md 报告（例外：PROJECT_BRIEF 认知卡、docs/memory 记忆体系为用户批准的基础设施）
- 状态：已采纳

## ADR-011 · PM 自主推进授权（R15 收官）
- 日期：2026-11-23
- 背景：用户明确"不需要等我放行，你是项目经理，你决策，完成我的任务就行"
- 决策：R15 各轮由 PM 自主派活、过闸、推进，不再逐轮等放行；每轮仍照常汇报（账本卡+≤10 行）；仅"需用户亲手操作"项（托盘退出实测、企微 webhook URL）保留等待；闸门纪律（一任务一审查、PASS 才进）不变
- 状态：已采纳

## ADR-012 · 活动门槛凌晨空闲豁免口径
- 日期：2026-11-23（PM 依 ADR-011 授权拍板）
- 背景：soak 门槛三"每小时活动增量>0"在凌晨 01:58~07:58 全 0，且截屏增量同刻全 0、应用 health ok——符合"夜间空闲/智能暂停"设计行为，非采集链路故障
- 决策：空闲时段（截屏增量=0 且用户无操作）豁免活动门槛；但重跑 soak 必须包含 ≥2 个活跃小时且活动增量>0，证明采集链路活着；豁免口径写入重跑验收标准
- 取舍：避免把"用户睡觉"误判成"应用坏了"；用活跃小时正增量兜底防真故障被豁免掩盖
- 状态：已采纳
